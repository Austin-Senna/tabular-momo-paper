\section{Introduction}

Consider an agent answering a question over a public-data lake: ``\textit{What was the median household income in counties affected by the 2020 wildfires?}'' The agent searches for fire-incidence data, finds a relevant dataset, peeks the schema, writes a SQL query joining on county FIPS codes, and gets back zero rows. It retries with different date filters, gets zero rows again, switches to a second candidate dataset, re-peeks, re-queries, then circles back to the first source, eventually exiting over budget without an answer. Retrieval was never the problem. The right datasets sat in the first few search results. The agent simply could not decide when to commit to a source, when to stop trying, or how to recover from a parsing failure without polluting its own context with hundreds of lines of error output.

This vignette captures what we call the \emph{stopping-rule illusion}: the belief that better retrieval automatically produces better tabular agents. It does not. Text-centric Agentic RAG systems~\cite{lewis2020rag,trivedi2023ircot,jiang2023flare,asai2024selfrag,yao2023react} were designed around a one-shot abstraction: a passage either is or is not relevant, and reading it costs roughly one tool call. Exploratory question answering over tabular data lakes~\cite{wang2026lakeqa} breaks that abstraction. A useful table requires schema inspection, file-handle resolution, code execution, parsing repair, and a deliberate stopping decision. Each candidate source represents a multi-turn commitment, not a single read.

We argue that this turns exploratory tabular QA into an \textbf{execution-discipline problem}, not (only) a retrieval one. The agent must know how to bound its commitment to a source, how to keep low-level wrangling artifacts (schemas, tracebacks, row dumps) out of its own reasoning context, and how to report partial progress when one source covers some but not all of the required outputs.

\paragraph{Tabular MOMO.} We introduce \textbf{MOMO} (Multi-Agent Orchestration for Multi-Source Observation), a runtime-control framework for exploratory tabular QA. MOMO is built on three roles. A \emph{planner} decomposes the question and orchestrates work without touching raw data tools. A \emph{search subagent} discovers candidate datasets under a small retrieval budget. An \emph{inspect subagent} works inside an explicit source family to extract the planner's requested outputs. The planner is deliberately prevented from directly searching, inspecting files, writing SQL, downloading data, or executing code; instead, it receives compact subagent returns containing candidate sources, answer fragments, missing outputs, evidence, retry recommendations, and budget statistics. We call this the \emph{context firewall}: raw schemas, SQL errors, row dumps, and parsing failures remain inside bounded workers rather than polluting the planner's reasoning.

Each subagent return uses an explicit four-value status (\texttt{success}, \texttt{partial}, \texttt{failed}, \texttt{budget\_exhausted}). The partial-success case is load-bearing: a worker that finds 2019 and 2020 data but not 2021 returns the fragments it has plus \texttt{missing\_outputs=[2021]}, rather than silently failing or forcing the planner to inspect a raw trace.

\paragraph{Contributions.} This workshop paper makes five contributions:

\begin{enumerate}
\item A \textbf{failure analysis} of agentic RAG on tabular data lakes that distinguishes retrieval failures from execution-discipline failures and identifies six concrete mechanisms by which text-centric Agentic RAG breaks down on tabular sources.
\item \textbf{Tabular MOMO}, a contract-based multi-agent architecture for exploratory tabular QA, with explicit search and inspect contracts and a restricted planner tool surface.
\item A \textbf{context firewall} mechanism implemented via bounded subagent return schemas, including a partial-success protocol that surfaces structured \texttt{missing\_outputs} rather than raw artifacts.
\item Runtime-control \textbf{ablations} exposed as separable feature flags (\texttt{results}, \texttt{cot}, \texttt{sprint}, \texttt{delegation}) on top of an existing \texttt{DataLakeAgent} harness, with \texttt{sprint} (single-agent commitment control) and \texttt{delegation} (multi-agent contract-based control) presented as alternative runtime-control strategies.
\item An \textbf{evaluation harness} supporting multi-axis ablations over search mode, planning mode, computation mode, and MOMO features under shared tasks, budgets, traces, and logs.
\end{enumerate}

\paragraph{Relation to the companion ablation framework.} MOMO is one runtime-control intervention. The companion SANA framework, applied to the same benchmark and codebase, isolates \emph{where} the bottleneck is by idealizing the search, planning, and execution axes. We view the two papers as complementary: SANA tells us that execution discipline is the residual bottleneck after retrieval is idealized; MOMO is one structured response to that bottleneck.
