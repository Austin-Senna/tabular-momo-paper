\subsection{Delegation Runtime Lifecycle (Pseudocode)}

\begin{verbatim}
def run_inspect_contract(contract):
    validate_schema(contract)
    worker = spawn_agent(
        tool_surface = INSPECT_TOOLS,
        guards       = [FileReferenceGuard(),
                        InspectSourceGuard(
                          allowed=contract.source_family_ids)],
        budget_steer = SubagentBudgetSteer(
                          budget=contract.budget_calls,
                          grace=1),
        ledger       = SubagentToolLedger(),
    )
    inject_system_prompt(worker, contract)
    while not worker.done:
        worker.step()
        if worker.budget_exhausted():
            return forced_return(worker, status="budget_exhausted")
    return validate_return(worker.last_contract_return)
\end{verbatim}

The search lifecycle is structurally identical; the differences are the tool surface (\texttt{SEARCH\_TOOLS} instead of \texttt{INSPECT\_TOOLS}) and the omission of \texttt{InspectSourceGuard}.

\subsection{Runtime Guards}

\paragraph{\texttt{\_FileReferenceGuard}.} A \texttt{SteeringHandler} subclass that intercepts tool calls before execution. It blocks (a) any call referencing a dataset only by \texttt{dataset\_id} without an accompanying \texttt{file\_path} or \texttt{s3\_uri}; and (b) any call whose \texttt{s3\_uri} is outside the data-lake bucket allowlist. Blocked calls return a structured contract-violation error the worker can act on.

\paragraph{\texttt{\_InspectSourceGuard}.} A second \texttt{SteeringHandler} subclass that restricts an inspect worker to the \texttt{source\_family\_ids} declared in its contract. Tool calls referencing other datasets or file paths are blocked at the runtime layer.

\subsection{Optional Runtime Controls (Detail)}

\paragraph{\texttt{results} --- profile-enriched peeks.} The \texttt{peek\_file} and \texttt{peek\_multiple} wrappers delegate to the baseline implementation and then attach a \texttt{profile} field loaded from \texttt{data/datagov\_tables\_profiles.jsonl} (precomputed) or from the ideal-search wrapper's schema cache. The profile contains schema columns, table kind, LLM-authored description, snippet, optional row counts, top rows, and per-column statistics (null rate, distinct count, min/max/mean for numeric columns). If no profile is available the field is omitted silently. The tool docstring instructs the agent to read the profile before issuing more expensive queries.

\paragraph{\texttt{cot} --- structured pre/post-tool records.} The \texttt{cot} tool takes two kinds. \texttt{kind="pre\_tool"} fields: \texttt{intended\_tool}, \texttt{current\_step}, \texttt{intent}, \texttt{confidence}. \texttt{kind="post\_tool"} fields: \texttt{completed\_tool}, \texttt{current\_step}, \texttt{tool\_result\_summary}, \texttt{next\_step}, \texttt{sufficient\_to\_call\_step\_complete}, \texttt{remaining\_gap\_if\_not\_complete}. The \texttt{CoTSteerHandler} plugin cancels any data-tool call that lacks a preceding pre-tool record, and appends a post-tool schema reminder to tool results to make compliance more attention-grabbing than a system-prompt-only directive.

\paragraph{\texttt{sprint} --- single-agent commitment control.} The \texttt{sprint\_block()} function emits one of two persistent prompt blocks. \emph{Cadence:} ``Every $k$ counted tool calls, call \texttt{sprint(kind="cadence", state\_of\_task=\dots)} before continuing. The runtime blocks additional tool calls until you do.'' \emph{Commitment:} ``Before working on a new source, call \texttt{sprint(kind="commitment\_contract", current\_source, commitment\_goal, max\_source\_calls, plan\_step)}. On budget exhaustion or source switch, call \texttt{sprint(kind="commitment\_reflection", potential\_answer, answer\_confidence, settled\_facts, short\_forward\_plan)}.'' In both modes the \texttt{sprint} tool writes a \texttt{\#\# CURRENT SPRINT} section into the agent's system prompt via an \texttt{upsert\_prompt\_section} helper, so the commitment is visible to the model on every subsequent turn without rederivation.

\subsection{CLI Flags}

The CLI entrypoint \texttt{run\_sana\_eval.py} exposes the configuration surface used in Section~\ref{sec:experiments}:

\begin{itemize}
\item \texttt{--search\_tool} $\in$ \{naive, preloaded, standard, ideal\}.
\item \texttt{--search\_results} $\in$ \{naive, preloaded, standard, ideal\}.
\item \texttt{--agent\_management} (alias \texttt{--plans}) $\in$ \{naive, preloaded, standard, ideal\}.
\item \texttt{--computation\_tool} $\in$ \{standard, ideal, $\ldots$\}.
\item \texttt{--max\_tool\_calls N}, \texttt{--k N} (macro-reflection cadence).
\item \texttt{--sana-feature \{sprint,cot,results,delegation\}} (repeatable).
\item \texttt{--sprint-mode \{cadence,commitment\}}, \texttt{--commitment-budget-calls N}.
\item \texttt{--max-search-subagent-calls N}, \texttt{--max-inspect-subagent-calls N}.
\end{itemize}

A friendly preset wrapper provides reproducible smoke and full evaluation configurations.

\subsection{Flag Composition Matrix}

\begin{table}[h]
\caption{Composition of MOMO feature flags. ``A'' = allowed; ``X'' = forbidden (validated at config time).}
\label{tab:flag-matrix}
\centering
\begin{tabular}{lcccc}
\toprule
 & results & cot & sprint & delegation \\
\midrule
results     & A & A & A & A \\
cot         & A & A & A & A \\
sprint      & A & A & A & X \\
delegation  & A & A & X & A \\
\bottomrule
\end{tabular}
\end{table}

The \texttt{sprint}/\texttt{delegation} mutual exclusion reflects the architectural choice to treat them as alternative control-plane strategies. The other three flags are independent: any subset can be enabled together. All flags default to off, in which case \texttt{SanaDataLakeAgent} reduces to the baseline \texttt{DataLakeAgent} (modulo the optional summarizing conversation manager).
